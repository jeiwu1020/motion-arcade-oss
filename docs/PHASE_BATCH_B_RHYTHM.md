# Batch B — Rhythm Motion / 節奏動一動

Updated: 2026-09-14

## Outcome and status

Rhythm Motion is a bounded, single-player, 60-second body-motion rhythm game
for smartphone landscape and projector play. The player reads four large note
lanes and performs one action at a time as each note reaches the hit zone.
Active play is an opaque Phaser stage; the camera is used only for explicit
setup, upper-body framing, Pose readiness, and tracking recovery.

Engineering status: `ENGINEERING PASS`.

Portfolio status: `PHYSICAL QA PENDING`.

Engineering PASS means the software loop, deterministic rules, normalized
Session, route lifecycle, and acceptance checks are complete. It does not claim
Windows Chrome, iPhone Safari, compact-space, projector, recognition, fatigue,
or physical timing validation. Shared Pose thresholds and shared camera
semantics are unchanged.

## Player loop

The immediate loop is:

`read the next symbol → perform one matching body action → see the grade/combo → read the next symbol`.

The 3-second countdown introduces all four actions in order: `LEFT`, `RIGHT`,
`REACH_LEFT`, `REACH_RIGHT`. The 60-second round then moves through:

| Round time | Rhythm phase | Intent |
|---|---|---|
| 0–15 s | `WARM_UP` | Teach each action at a 1,000 ms beat. |
| 15–35 s | `GROOVE` | 900 ms seeded patterns. |
| 35–50 s | `ENERGY` | 800 ms bounded pattern changes. |
| 50–60 s | `FINAL_BEAT` | 750 ms legal spacing, stronger pulse and stage motion. |

There are no simultaneous notes, no CLAP detector, no early game-over, and no
clinical reaction-time claim. A MISS is readable but non-punitive and the round
continues.

## Four-action input contract

Rhythm Core exposes only its small game-local action enum:

| Game action | Production normalized sources | Meaning |
|---|---|---|
| `LEFT` | `MOVE_LEFT` or `LEAN_LEFT` | Shift or lean left without walking across the room. |
| `RIGHT` | `MOVE_RIGHT` or `LEAN_RIGHT` | Shift or lean right without walking across the room. |
| `REACH_LEFT` | `REACH_LEFT` | Reach toward the left target. |
| `REACH_RIGHT` | `REACH_RIGHT` | Reach toward the right target. |

`RhythmSession` consumes only new provider sequence occurrences. It marks
current sequences at start and replay, consumes new occurrences during readiness
loss, and advances Core time only while `setupReady` is true and no hard failure
is present. Developer and production routes use this same bridge.

## Chart generation and fairness

The chart is pre-generated by the framework-independent Core with a seeded
linear congruential generator. `Math.random` is never used by gameplay. The
same seed reproduces action order, target times, phase transitions, and replay.

A bounded pattern library covers side swaps, reach swaps, cross-side moves, and
four-step phrases. The generator enforces these safety rules:

- no adjacent identical actions;
- no more than two consecutive actions from the same body side;
- no simultaneous target times;
- no note gap below 750 ms;
- every target remains inside the 60-second round;
- one action occurrence resolves at most one nearest eligible matching note;
- the ±350 ms GOOD window leaves a deliberate gap between adjacent note windows.

The Core stores each note as immutable data: id, game-local action, target time,
and `PENDING`/`PERFECT`/`GREAT`/`GOOD`/`MISS` resolution. Phaser derives travel
position from elapsed time, target time, and the 2,000 ms visual lead; it never
decides judgement.

## Judgement and scoring

Timing is symmetric around a note target:

- `PERFECT`: absolute offset ≤120 ms;
- `GREAT`: >120 ms through 230 ms;
- `GOOD`: >230 ms through 350 ms;
- `MISS`: outside ±350 ms once the late edge passes.

Scores are 150 / 120 / 90 / 0 for PERFECT / GREAT / GOOD / MISS. A successful
note increments combo; a MISS resets it. Every completed five-combo tier adds
10 points to that note, capped at +50. Score never decreases. Results show
score, successful notes, misses, best combo, and grade counts.

For every successful note Core retains `hitOffsetMs` and aggregates early hits,
late hits, total absolute offset, and mean absolute offset. The normal HUD does
not show raw timing. Developer results expose a compact `節奏準度` diagnostic;
these values are engineering/gameplay metrics, not medical measurements.

## Production Pose and camera behavior

The production route uses the existing `PoseMotionInputProvider` and
`PoseGameplayInputRuntime` with the `UPPER_BODY` ability profile and this exact
request:

`MOVE_LEFT`, `MOVE_RIGHT`, `LEAN_LEFT`, `LEAN_RIGHT`, `REACH_LEFT`, `REACH_RIGHT`.

The shared `CameraPresentationStage` provides explicit camera permission,
mirrored preview, upper-body guide, existing readiness states, and deterministic
dispose. Setup copy asks the player to keep head, shoulders, arms, wrists,
torso, and hips visible. No knees/ankles, CLAP, microphone, new detector, or
threshold change is introduced.

While ready and playing, the opaque rhythm stage is visually dominant. If
tracking is lost, Core time pauses and the shared camera/recovery guidance
returns to dominance; READY resumes from the same chart state. Opening Home or
the game route does not request media automatically.

## Presentation and Final Beat

The Phaser stage is a logical `1280 × 720` four-lane playfield ordered as LEFT,
REACH_LEFT, REACH_RIGHT, RIGHT. Each lane has both a distinct symbol/shape and
visual treatment: directional arrows, ring-and-reaching targets, and separate
cyan, amber, green, and pink treatments. Color is never the only signal.

Notes travel for approximately 2,000 ms toward a bright bottom hit zone. A
chart-linked pulse expands the stage/hit zones near the next target. Successful
notes burst visually into large PERFECT/GREAT/GOOD feedback and preserve the
next-note read; MISS fades as a small non-punitive status. Final Beat adds a
stronger pulse, richer side streaks, a `FINAL BEAT!` announcement, and faster
but still legal travel pacing.

No production music or synthesized placeholder audio is required for this
engineering pass. The complete visual loop remains understandable without
audio; licensed music/chart synchronization and production SFX are polish work.

## Engineering evidence and deferred QA

The engineering gate includes deterministic Core and Session tests, exact
judgement boundary tests, combo/scoring/metrics coverage, registry/navigation
coverage, explicit-permission production-route coverage, typecheck, lint, full
tests, build, and `git diff --check`. Developer and production landscape smoke
checks cover Home, route launch, four actions, countdown/play/result/replay,
upper-body setup, no automatic camera/microphone request, and overflow.

The later physical QA sweep must evaluate each action and note type on Windows
Chrome, iPhone Safari landscape, compact space, and projector: setup/readiness,
recognition, false positives/negatives, timing, fatigue, readability, game
feel, audio, recovery, and lifecycle cleanup. Shared thresholds may change only
after that cross-game evidence is collected in an explicit foundation batch.
